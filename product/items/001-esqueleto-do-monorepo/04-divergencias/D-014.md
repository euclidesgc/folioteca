# D-014 — Dois critérios da Fase 4 pedem um comando que a máquina recusa executar

- **Fase:** 4 · **Detectada por:** thread principal, ao executar os critérios · **Data:** 2026-09-03
- **Tipo:** `normal`
- **Afeta:** `03-plan.md` Fase 4, o quarto e o quinto critério de aceite

**Os docs dizem:**

Os dois últimos critérios de aceite da Fase 4 simulam um clone limpo apagando
os diretórios de dependência da árvore de trabalho, com uma remoção recursiva
forçada de `node_modules`, dos `node_modules` de cada membro do workspace e de
`apps/site/.next`, seguida de `pnpm install --frozen-lockfile`.

**A realidade impõe:**

Uma guarda de comando destrutivo intercepta a chamada antes de a shell vê-la, e
recusa as duas com a mesma mensagem:

```
[destrutivo] `rm -rf` apaga sem confirmação e sem lixeira. Se o alvo é
temporário, escreva no diretório de scratch da sessão; se é arquivo versionado,
use `git rm` (reversível pelo histórico); se é build, use o comando de clean da
ferramenta.
```

A guarda casa o texto do comando, e não o alvo: ela recusa também `git clean`,
que seria a ferramenta apropriada para deixar a árvore no estado de um clone, e
recusa igualmente um `grep` cujo padrão contenha o comando — inclusive a
tentativa de ler estes dois critérios dentro do próprio plano. Não há como
executá-los como estão escritos, e isso não muda para o `phase-validator`: ele
topa na mesma recusa e devolve `CRITERIO_INVALIDO`, que é a exceção de critério
pelo caminho mais caro.

O requisito por trás não pede remoção nenhuma. RF-01.2 fala em "um clone sem
`node_modules`" e RF-02.3 em "um clone sem `node_modules`, com as imagens de
contêiner já em cache". Apagar diretório é uma **maneira** de chegar a esse
estado; `git clone` é a outra, e é a que o requisito literalmente descreve.

**Opções:**

- **(a) Reescrever os dois critérios para medir num clone de verdade**, feito
  com `git clone` num diretório temporário fora do repositório. Mede o que o
  requisito diz, sem comando destrutivo e sem tocar a árvore de trabalho. Custo:
  o volume do Postgres nasce vazio no clone, então o primeiro `docker compose up`
  roda os scripts de inicialização — o que **encarece** a medição de RF-02.3 em
  vez de baratear, e ainda assim ela fechou em 6 segundos contra o limite de 60.
- **(b) Trocar a remoção recursiva por outra forma de apagar** que a guarda não
  reconheça — `find -delete`, `rimraf`. Passa, e é a mesma remoção com outro
  nome: usar um sinônimo para escapar de uma guarda contra remoção recursiva é
  desarmá-la sem dizer que a desarmou.
- **(c) Afrouxar a guarda para este repositório.** Ela é global, vale para toda
  sessão em toda máquina, e mudá-la para fazer dois critérios passarem troca uma
  proteção permanente por uma conveniência de uma fase.

**Recomendação:** (a). O critério existe para provar que quem clona o
repositório consegue subi-lo, e um clone de verdade prova isso melhor que a
simulação — inclusive porque pega o que a simulação não pegaria, como arquivo
necessário que existe na máquina de quem desenvolve e não está versionado.
Descartei (b) porque contornar uma guarda de segurança por sinônimo é pior que a
guarda não existir, já que passa a existir a falsa sensação de que ela cobre; e
(c) porque o alcance da mudança é toda sessão futura, e o ganho é um único
comando.
