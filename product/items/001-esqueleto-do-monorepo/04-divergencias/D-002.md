# D-002 — A opção Joi que o plano fixa para remover as aspas do rótulo não existe

- **Fase:** 2 · **Detectada por:** nest-implementer · **Data:** 2026-09-02
- **Tipo:** `normal`
- **Afeta:** `03-plan.md` Fase 2, etapa 2.3

**Os docs dizem:**

Etapa 2.3: criar o schema "com a opção Joi `errors: { wrap: { label: '' } }`".
A justificativa da etapa explica o porquê: sem ela a mensagem sai com o nome
entre aspas e deixa de ser a linha `DATABASE_URL is required` que o critério
comportamental de RF-05.3 exige literalmente.

**A realidade impõe:**

`errors.wrap.label` não aceita string vazia. Na versão resolvida (`joi@18.2.5`,
e o mesmo em `17.13.3`) a chamada lança `AssertError: "errors.wrap.label" is not
allowed to be empty` **na construção do schema** — antes de qualquer validação.
O efeito não seria uma mensagem malformada no cenário de variável faltando: o
processo quebraria sempre, inclusive com o `.env` completo.

**Opções:**

- **(a) `errors: { wrap: { label: false } }`** — é a forma documentada do Joi
  para desativar o embrulho do rótulo, e produz exatamente
  `DATABASE_URL is required`. Uma palavra muda na etapa; o critério de aceite
  não cita a opção e fecha como escrito.
- **(b) Manter a opção literal e reescrever a mensagem à mão** com
  `.messages({ 'any.required': '{#label} is required' })` por chave — funciona,
  mas duplica o texto do requisito em cada campo e faz variável nova nascer sem
  a regra.
- **(c) Remover as aspas no consumidor**, tratando a string em `main.ts` —
  põe conhecimento do formato do Joi na camada de bootstrap e quebra quando o
  Joi mudar a mensagem.

**Recomendação:** (a). O plano fixou um **método** e errou o valor dele; o
critério de aceite cobra a linha `DATABASE_URL is required`, e é ela que (a)
produz. (b) espalha o texto do requisito por cada chave, que é o defeito que a
própria etapa 2.3 quis evitar; (c) põe o formato de mensagem de uma biblioteca
dentro do bootstrap.
