# D-006 — O script que gera o contrato é TypeScript e nenhuma etapa declara o que o executa

- **Fase:** 2 · **Detectada por:** nest-implementer · **Data:** 2026-09-02
- **Tipo:** `normal`
- **Afeta:** `03-plan.md` Fase 2, etapa 2.1 e etapa 2.8

**Os docs dizem:**

Etapa 2.8: criar `apps/api/scripts/generate-openapi.ts` — um arquivo
TypeScript. Etapa 2.1: declarar o script `openapi:generate` no manifesto. A lista
de dependências de desenvolvimento da etapa 2.1 traz `typescript`, `jest`,
`ts-jest`, `@nestjs/cli` e os tipos, mas nenhum executor de TypeScript para um
script avulso.

**A realidade impõe:**

`ts-jest` só executa dentro do Jest e o `@nestjs/cli` compila a aplicação, não um
script de `scripts/`. `node --experimental-strip-types` remove os tipos mas não
processa `emitDecoratorMetadata`, e o documento OpenAPI é montado a partir
exatamente dos decoradores (`@ApiProperty`, `@ApiOkResponse`) — sem os metadados,
o contrato sai vazio de schema. O critério `comando` de RF-07.3 executa
`pnpm --filter api run openapi:generate`, então o script precisa rodar.

**Opções:**

- **(a) `ts-node --transpile-only`** — executa o script com os decoradores
  intactos, e `--transpile-only` evita pagar a checagem de tipos de novo, que o
  script `typecheck` já faz num passo próprio.
- **(b) Compilar antes e executar o JavaScript de `dist/`** — dispensa a
  dependência nova, mas amarra a geração do contrato a um build anterior e
  transforma um comando em dois, com a chance de gerar o contrato a partir de um
  `dist/` velho, que é precisamente a divergência silenciosa que o job de
  contrato existe para pegar.
- **(c) Reescrever o script em JavaScript** — dispensa executor, mas o script
  importa `AppModule` e os DTOs, que são TypeScript, e perderia a checagem de
  tipos sobre o próprio código que produz o contrato.

**Recomendação:** (a). É a forma mais comum no ecossistema NestJS e a mais
reversível — sai numa linha se o `node` passar a processar decoradores.
Descartei (b) porque contrato gerado de artefato compilado velho é a falha que o
gate de contrato deveria detectar e passaria a causar, e (c) porque tiraria a
checagem de tipos justamente de onde o contrato nasce.
