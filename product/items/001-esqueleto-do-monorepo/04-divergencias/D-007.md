# D-007 — Silenciar o logger para limpar o boot cega a API pela vida inteira do processo

- **Fase:** 2 · **Detectada por:** security-auditor · **Data:** 2026-09-02
- **Tipo:** `normal`
- **Afeta:** `03-plan.md` Fase 2, etapa 2.7; substitui a solução ratificada em
  `D-004`

**Os docs dizem:**

A etapa 2.7, já reconciliada por `D-004`, manda criar `main.ts` com
`NestFactory.create(AppModule, { abortOnError: false, logger: false })` dentro de
`try`/`catch`. O `logger: false` entrou porque `abortOnError: false` sozinho não
impede o `ExceptionHandler` do Nest de imprimir stack trace, e o critério
comportamental de RF-06.2 exige uma única linha em `/tmp/boot.log`.

**A realidade impõe:**

`logger: false` não é escopo de bootstrap. Ele chama `Logger.overrideLogger(false)`,
que zera o `staticInstanceRef` **estático e global** do `Logger`, e o efeito dura
o processo inteiro. Medição do auditor, em processos isolados, mesma aplicação,
mesma exceção lançada de um handler:

```
logger=false   → resposta 500 ao cliente | 0 bytes logados    | Logger da app: NÃO
logger=padrão  → resposta 500 ao cliente | 2982 bytes logados | Logger da app: SIM
```

Depois que a API sobe, toda exceção não tratada devolve `500` ao cliente e **não
deixa registro nenhum no servidor**: o `ExceptionsHandler` do Nest escreve pelo
mesmo `Logger` estático. Quem sonda a API provocando 500s em série não deixa
rastro. Colide com a norma "log estruturado com correlação", e qualquer `Logger`
que o item `002` escrever nasce mudo — sem erro, só silêncio, que é a forma mais
cara de descobrir tarde.

**Opções:**

- **(a) Validar o ambiente antes de `NestFactory.create`** — chamar
  `environmentSchema.validate(process.env)` no topo do `main.ts`, imprimir as
  variáveis faltantes e sair ali. O Nest nunca chega a subir no cenário de
  configuração inválida, então não há stack trace a suprimir e o `logger: false`
  perde a razão de existir. O `ConfigModule.forRoot` com `validationSchema`
  permanece no `app.module.ts`, como o critério estrutural cobra: é o mesmo
  objeto `environmentSchema`, aplicado mais cedo, não uma segunda regra.
- **(b) Manter `logger: false` e reativar o logger depois do `listen`** — o dano
  fica restrito ao boot, mas depende de uma linha que ninguém vai lembrar de
  manter, e o intervalo entre `create` e `listen` continua mudo.
- **(c) Escrever um `LoggerService` que descarte só o erro de inicialização** —
  correto e caro: constrói agora, para um caso que dura milissegundos, a peça
  que o log estruturado do item `002` vai construir de qualquer jeito.

**Recomendação:** (a). É a opção que `D-004` havia descartado por "duplicar a
validação", e o argumento não se sustenta diante da medição: não são duas
regras, é o mesmo schema aplicado antes de o framework existir. O custo que
`D-004` não conhecia — a API muda em runtime — é maior em uma ordem de grandeza
que o custo de importar o schema em dois lugares. Descartei (b) por depender de
disciplina para não regredir, e (c) por antecipar trabalho do item `002` sem
necessidade.

**Status:** RECONCILIADA
