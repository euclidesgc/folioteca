Sessão de reconciliação de `D-007` a `D-010`. Um sintoma, duas metades: a que

## 1. Agent do plugin não casa com política nenhuma, e os guards liberam

### Sintoma

O `doc-reconciler` foi despachado para reconciliar um documento aprovado — o
caso exato que o guard existe para permitir — e foi recusado:

```
[doc aprovado] `product/items/001-esqueleto-do-monorepo/03-plan.md` foi aprovado
em 2026-09-02T09:56:27Z. Documento canônico não muda por edição direta: (...)
a reconciliação é feita pelo `doc-reconciler` depois da aprovação humana.
```

O guard recusou o `doc-reconciler` dizendo que quem faz aquilo é o
`doc-reconciler`. O fluxo `/harness:reconcile` está morto de ponta a ponta: sem
exceção de critério aberta à mão, nenhum documento aprovado se reconcilia.

O mesmo desencontro, no ramo de cima do mesmo arquivo, falha para o outro lado.
Medição com o evento real alimentado aos hooks, antes da correção do projeto:

```
harness:scout      Write em apps/api/src/main.ts   -> allow   (deveria negar)
harness:scout      Task para outro agent           -> allow   (deveria negar)
harness:doc-writer Write em apps/web/src/x.ts      -> allow   (deveria negar)
```

Nove agents de leitura pura ou de escopo estreito escreviam em qualquer caminho
e delegavam à vontade. Depois da correção do projeto, os três negam.

### Frequência

Permanente, em toda sessão, desde a instalação. Atinge os nove agents que o
plugin fornece — `scout`, `doc-writer`, `plan-writer`, `phase-validator`,
`criteria-auditor`, `divergence-auditor`, `doc-reconciler`, `security-auditor`
e `test-runner`. Não atinge os cinco agents locais do projeto, cujo nome chega
nu e casa com a matriz.

### Diagnóstico

`_hooklib.active_agent` devolve o `agent_type` do evento verbatim. Quando o
agent vem de um plugin, o Claude Code o namespaceia: `harness:doc-reconciler`,
não `doc-reconciler`. As duas comparações a jusante são por igualdade nua:

| Arquivo | Linha | Comparação | Efeito do desencontro |
|---|---|---|---|
| `scripts/hooks/guard_write.py` | 29, 106 | `agent == "doc-reconciler"` | reconciler nunca reconhecido — **falha fechado** |
| `scripts/hooks/guard_write.py` | 74 | `matrix["agents"].get(agent)` | sem política → `return None` — **falha aberto** |
| `scripts/hooks/tool_ladder_guard.py` | 55 | `matrix["agents"].get(agent)` | sem política → `return allow` — **falha aberto** |

O que torna a classe cara não é nenhum dos três isolados: é que a mesma premissa
errada — "o nome do agent é nu" — produz recusa indevida num ramo e liberação
silenciosa no outro. A liberação não emite nada. Ninguém descobre que a
fronteira sumiu; descobre-se que o reconciler não passa, e o furo continua.

O teste do próprio harness carrega a premissa: `test/hooks-protocol.test.mjs`
usa `agent_type: "scout"` e `subagent_type: "outro"`, nomes nus, então a suíte
passa contra um ambiente que não é o real.

### Roteamento

| Sintoma | Destino |
|---|---|
| Premissa errada sobre o formato do nome | `scripts/hooks/_hooklib.py`, `active_agent` |
| Teste que não reproduz o ambiente real | `test/hooks-protocol.test.mjs` |

**Arquivos a mudar:** `scripts/hooks/_hooklib.py`, `test/hooks-protocol.test.mjs`

### Mudança proposta

Normalizar no único ponto onde a identidade é resolvida, em vez de ensinar cada
consumidor a lidar com prefixo. `active_agent` passa a devolver o nome nu,
descartando o namespace do plugin quando houver:

```python
# o Claude Code namespaceia agent de plugin: "harness:scout".
# a política é escrita por nome, então a identidade se resolve por nome.
if ":" in agent:
    agent = agent.rsplit(":", 1)[-1]
```

Com isso, `RECONCILER` volta a casar, as duas buscas na matriz voltam a achar
política, e a matriz do projeto pode continuar escrita com nome nu — que é como
o instalador a gera hoje.

Junto, a suíte passa a exercitar o nome namespaced: um caso com
`agent_type: "harness:scout"` provando que a negação acontece. Sem esse caso, a
correção não tem quem a defenda.

### O que isto NÃO é

Não é mudança de skill nem de norma. A fronteira de agent está certa como regra
e a `tool-matrix.json` está certa como formato; o que está errado é a chave com
que o harness procura nela.

### Nota sobre o que o projeto já fez

O commit `a1eae02` prefixou as nove chaves da `.harness/tool-matrix.json` para
`harness:<nome>` e acrescentou
`scripts/gates/__tests__/fronteira-de-agent.test.sh` ao fluxo `Portões`. Isso
fecha o furo **neste projeto** e nada mais — a classe segue em qualquer outro
que instale o harness.

Quando esta proposta for aplicada, as duas grafias passam a funcionar e a
prefixação no projeto vira redundante, não errada. Desfazê-la é opcional; o
teste que a acompanha continua valendo, porque o que ele afirma é a simetria
entre a matriz e os agents que existem, não a grafia da chave.
