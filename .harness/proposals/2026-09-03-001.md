# Proposta 2026-09-03-001 — O `state.py` grava no `product/state.json` do diretório corrente, e diz que deu certo

**Sessão:** 2026-09-03 · **Item(ns):** `001-esqueleto-do-monorepo` · **Fases:** 4

Duas ocorrências no mesmo dia, na mesma fase, pela mesma causa. As duas foram
remendadas à mão; esta proposta existe para a terceira não acontecer. O projeto
já se defendeu com um wrapper (`scripts/harness/state.sh`), mas o wrapper é
disciplina de chamador: basta alguém digitar o comando do jeito que o próprio
`prompt-da-proxima-sessao.md` ensinava para o defeito voltar.

---

## 1. Estado gravado no clone temporário, com saída de sucesso

### Sintoma

`state.py` resolve o `product/state.json` a partir do **diretório corrente**
quando não recebe `--root`. O diretório corrente de uma sessão sobrevive entre
chamadas de Bash. Os critérios de aceite da Fase 4 mandam medir dentro de um
clone temporário — decisão registrada em `D-014`, e a recomendação certa. Basta
o `cd` do critério para que toda chamada seguinte caia no repositório errado.

**Primeira ocorrência — o agent foi mandado refazer trabalho já feito:**

```
$ cd /tmp/<clone>
$ git hash-object product/items/001-esqueleto-do-monorepo/03-plan.md
<sha do arquivo do clone, não o do repositório>
```

O caminho relativo leu o plano do clone. A conclusão foi que um agent não havia
escrito o que escreveu, e ele foi despachado de novo para refazer o trabalho.

**Segunda ocorrência — a divergência que não existia:**

```
$ cd /tmp/<clone>
$ python3 .../state.py diverge --id D-014 --phase 4 --kind normal
{ "id": "D-014", "status": "PENDENTE" }        <- exit 0
```

O comando imprimiu sucesso. A divergência foi gravada no `product/state.json` do
clone. No repositório real ela simplesmente não existia, e só apareceu porque
uma verificação posterior foi procurá-la.

Reproduzido contra o `state.py` real, fora de qualquer sessão:

```
cwd = /tmp/state-demo/clone   (o clone que o critério manda medir)
raiz do trabalho = /tmp/state-demo/projeto

--- chamada crua ao state.py ---
{ "created": "D-CRU", ... }                    <- sucesso
  gravou em projeto/product/state.json? 0
  gravou em clone/product/state.json?   2      <- lugar errado
```

### Frequência

Duas ocorrências em uma fase. A classe é larga: todo critério de aceite que mede
num clone, todo teste que roda num sandbox, todo `cd` para diretório de scratch.
O harness ensina a medir em clone — foi ele que criou a condição.

### Diagnóstico

`repo_root()` já faz o que parece a correção óbvia:

```python
def repo_root():
    out = subprocess.run(["git", "rev-parse", "--show-toplevel"], ...)
    if out.returncode == 0 and out.stdout.strip():
        return out.stdout.strip()
    return os.getcwd()
```

Ancorar na raiz do git **já é o comportamento atual**, e é exatamente ele que
falha: um clone temporário também é um repositório git, e `git rev-parse`
respondeu de dentro dele com confiança total. O `cd` não quebrou a âncora — ele
moveu o que a âncora mede.

Ou seja: o problema não é a falta de âncora, é a **ambiguidade**. Existem duas
respostas plausíveis para "qual projeto?", o `state.py` escolhe uma em silêncio,
e escolhe a errada em toda medição feita num clone. É a mesma forma que
`scripts/gates/medir.sh` existe para matar nos portões deste projeto — *consegui
medir?* fica implícita, e o comando responde à segunda pergunta como se a
primeira tivesse sido respondida.

O agravante é o código de saída. Uma escrita no lugar errado sai `0`, e o
chamador — que é o orquestrador — não tem como distinguir. Estado é a única
coisa do harness que ninguém revalida: o plano é lido, o código é revisado, o
veredicto é conferido; o `state.json` é acreditado.

### Roteamento

| Sintoma | Destino |
|---|---|
| Conhecimento que não estava em lugar nenhum | `scripts/state/state.py` e `scripts/hooks/load_state.py` |

**Arquivos a mudar:** `scripts/state/state.py` (resolução de raiz),
`scripts/hooks/load_state.py` (`export_plugin_root`)

### Mudança proposta

**Recusar quando a raiz for ambígua, em vez de escolher.**

O hook de início de sessão já conhece a raiz do projeto — ele a recebe como
argumento em `export_plugin_root(root)` — e já tem dois canais abertos para
levá-la adiante: o `CLAUDE_ENV_FILE` e o `.harness/runtime/plugin-root.json`.
Falta usá-los para isto:

```python
# load_state.py, em export_plugin_root
lib.write_json(
    os.path.join(root, lib.RUNTIME_DIRNAME, "plugin-root.json"),
    {"plugin_root": caminho, "project_root": root, "exported_at": lib.utc_now()},
)
handle.write(f'export HARNESS_PROJECT_ROOT="{root}"\n')
```

```python
# state.py, no lugar de repo_root()
def resolve_root(explicit):
    if explicit:
        return explicit
    sessao = os.environ.get("HARNESS_PROJECT_ROOT")
    corrente = git_toplevel(os.getcwd())
    if sessao and corrente and os.path.realpath(sessao) != os.path.realpath(corrente):
        raise AnchorError(
            f"raiz ambígua: a sessão abriu em {sessao} e o diretório corrente "
            f"pertence a {corrente}. Passe --root explicitamente."
        )
    return sessao or corrente or os.getcwd()
```

A recusa sai com código próprio — nem `0`, que mentiria, nem `1`, que o
`state.py` já usa para "transição recusada" e que o orquestrador precisa
distinguir de "o estado nem rodou".

**Por que recusar, e não ancorar melhor.** A outra correção possível era o
`state.py` ancorar sozinho na raiz do git quando `--root` não viesse. Ela é
tentadora e é o que ele já faz — e é o que falhou nas duas ocorrências, porque
um clone é um repositório git legítimo e responde ao `rev-parse` sem hesitar.
Nenhuma âncora que o `state.py` possa calcular sozinho sobrevive a um `cd` para
outro repositório: o script é genérico, mora no plugin, e o único sinal que ele
tem do projeto é o diretório de quem o chamou. Quando o sinal é ambíguo, não
existe escolha certa a fazer em silêncio — existe a obrigação de parar. É a
doutrina que o próprio harness escreveu em `medir.sh`: **não conseguir medir é
reprovação, nunca aprovação.**

O custo é baixo e assimétrico. Fora de sessão — CI, script solto —
`HARNESS_PROJECT_ROOT` não existe e nada muda. Dentro de sessão, a recusa só
aparece quando as duas respostas divergem, que é precisamente o instante em que
a gravação seria errada. E ela é acionável: a mensagem nomeia as duas raízes e o
`--root` que resolve.

### O teste que a provaria

Um sandbox com dois repositórios git, cada um com o seu `product/state.json`:
um faz de projeto, o outro de clone temporário. Com o corrente dentro do clone:

1. `HARNESS_PROJECT_ROOT=<projeto> state.py item-new --item T` **recusa**, com
   código próprio, e nenhum dos dois `state.json` muda;
2. `state.py --root <projeto> item-new --item T` grava no projeto;
3. sem `HARNESS_PROJECT_ROOT`, o comportamento de hoje continua — é o caminho
   do CI, e ele não pode passar a recusar;
4. com o corrente **dentro do projeto**, `HARNESS_PROJECT_ROOT=<projeto>` grava
   normalmente: a recusa é da divergência, não da variável.

O caso 1 é o que morde. Sem ele o teste passaria com o defeito presente — foi
essa a verificação que este projeto fez no seu próprio wrapper, rodando o mesmo
cenário contra a chamada crua e confirmando que ela erra onde o wrapper acerta
(`scripts/harness/__tests__/state.test.sh`).

### O que isto NÃO é

Não é remover o `--root`: ele continua sendo a resposta explícita e continua
tendo precedência sobre tudo.

Não é o wrapper. `scripts/harness/state.sh` resolve para este projeto e é
disciplina de chamador — ele só protege quem lembra de usá-lo, e quem lembra não
era o problema. A correção definitiva é o `state.py` recusar por conta própria,
e aí o wrapper vira conveniência em vez de defesa.

Não é caso isolado de dois comandos. `git hash-object` com caminho relativo caiu
na mesma armadilha na primeira ocorrência, e todo comando do harness que aceita
caminho relativo cai. O que fecha a classe é o estado parar de aceitar
ambiguidade — porque é o estado que ninguém revalida depois.
