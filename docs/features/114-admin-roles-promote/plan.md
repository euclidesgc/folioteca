  - O que fazer (D1, R5, R10, R11):

Nenhum outro caminho tem dois segmentos começando por `admins`; o único vizinho, `/admins`, tem **um** segmento. Não há identidade literal nem a identidade que a OpenAPI proíbe entre caminhos que só diferem pelo **nome** do parâmetro. Esta fatia **não** declara nenhum segmento literal sob `/admins` (um `/admins/count` casaria com `{personId}` no Nest conforme a ordem de declaração dos métodos), e a regra fica escrita para a 115. Nenhum caminho existente é renomeado e nenhum parâmetro muda de nome.

- [x] T1.2 — `promote` no serviço e `@Put(':personId')` no controller que já existe
  - Arquivos: `apps/api/src/admin-roles/admin-roles.service.ts` (alterar); `apps/api/src/admin-roles/admin-roles.controller.ts` (alterar)
  - O que fazer (D2, R5, R10, R11). **Nenhum arquivo novo na API**: nem módulo, nem DTO, nem guard.
    - `admin-roles.service.ts`: exportar `const PERSON_NOT_FOUND_MESSAGE = 'Pessoa não encontrada.';` (o teste assere a constante, nunca uma cópia do texto; **não** se importa a constante de `unit-assignments/` — são módulos independentes e a coincidência de texto não é contrato entre eles). Método novo, com o comentário `/** 200 também para quem já administra: promover é idempotente (R5). */`:

      ```ts
      async promote(organizationId: string, personId: string): Promise<AdminResponse> {
        const person = await this.prisma.person.findFirst({
          where: { id: personId, organizationId },
          select: adminFields,
        });

        if (!person) throw new DomainNotFoundException(PERSON_NOT_FOUND_MESSAGE);

        await this.prisma.person.updateMany({
          where: { id: personId, organizationId },
          data: { isAdmin: true },
        });

        return { data: person };
      }
      ```

    - **`findFirst` com `organizationId` no `where`, nunca `findUnique` por id**: é o que torna pessoa de outra organização indistinguível de inexistente (R11). **Sem `isUuid`**: id malformado simplesmente não é achado e cai no mesmo 404 — a mesma decisão, pela mesma razão já escrita em `unit-assignments.service.ts`.
    - **`updateMany`, e não `update`**: `update` por `id` deixaria a barreira de organização só na leitura anterior; `updateMany` carrega o escopo no próprio `where` e não estoura quando nada casa, que é o comportamento certo numa corrida.
    - **Idempotência sem `if`**: o serviço **não** lê `isAdmin` para decidir nada; gravar `true` sobre quem já é `true` devolve 200 e dois envios simultâneos escrevem o mesmo valor na mesma linha. Nada distingue "já era" de "acabou de ser".
    - **`select: adminFields` também aqui** (a constante já existe no arquivo): `Person` tem `passwordHash`, e o `select` é a barreira.
    - **O papel de quem chama não é caso especial**: promover a si mesmo é permitido e não muda nada.
    - `admin-roles.controller.ts`: um `@Put(':personId')` que recebe `@CurrentPerson() person` e `@Param('personId') personId: string` e devolve `Promise<AdminResponse>`. **Nenhum `@UseGuards` por método**: o `@UseGuards(SessionGuard, AdminGuard)` da classe já cobre o método novo, e é isso que o comentário que já está lá promete — ele permanece e passa a ser verdade demonstrada. O `CsrfGuard` global (`APP_GUARD`) cobre o `PUT` sem uma linha a mais. Sem `Logger` e sem `console.` fora de testes.
  - Skills: authorization, security
  - Complexidade: média
