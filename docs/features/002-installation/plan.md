# PLAN 002 — installation

Branch: `feature/002-installation`

Fonte: `docs/features/002-installation/spec.md` (as siglas D1…D14 são as decisões técnicas da SPEC e R1…R11 os requisitos do PRD; o texto necessário de cada uma está copiado na tarefa). Ambiente: Node 24, pnpm 11, TypeScript 5.9 strict, Prisma 6, NestJS 11 com SWC. Portas: web 5173, API 3000, Postgres 5433, web do e2e 5174.

Pré-condição de todas as fases: `docker compose up -d` na raiz (Postgres local). Comandos de verificação, sempre na raiz: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`. "Sem aviso" vale para os quatro.

Regras que valem para todas as tarefas:

- Nenhum código de instalação nem senha literal entra no repositório (o GitGuardian reprova). Nos testes: código gerado com `randomBytes`, senha válida com `crypto.randomUUID()`, senha curta com `'x'.repeat(11)`.
- Todo componente devolve `React.JSX.Element`; `ref` é prop comum (sem `forwardRef`); imports absolutos com `@/`; sem barrel files; arquivos em kebab-case.
- Nenhum arquivo de configuração novo. Todo arquivo novo de `src/` tem teste próprio: a cobertura conta arquivo nunca importado por teste.
- Tamanho da fatia (~1.300 linhas) já aceito na SPEC; não re-fatiar.

Desvio único em relação à tabela de arquivos da SPEC: a alteração de `docs/design.md` sai da fase 3 e entra na fase 2 (T2.1), porque a skill `interface-design` manda a receita nova entrar na mesma entrega da tela que a usa, e os critérios visuais da fase 2 apontam para essas receitas.
