- [ ] T1.2 — `demote` no serviço, dentro de transação com `SELECT … FOR UPDATE`, e `@Delete(':personId')` no controller
  - Arquivos: `apps/api/src/admin-roles/admin-roles.service.ts` (alterar); `apps/api/src/admin-roles/admin-roles.controller.ts` (alterar)
  - O que fazer (D2, D3, R5, R6, R11, R12). **Nenhum arquivo novo na API**: nem módulo, nem DTO, nem guard.
    - `admin-roles.service.ts`: exportar

      ```ts
      /** A frase é do domínio e aparece na tela: o teste assere a constante. */
      export const LAST_ADMIN_MESSAGE =
        'Esta é a única administração da instância. Promova outra pessoa antes de tirar o papel desta.';
      ```

      e o método `demote(organizationId: string, personId: string): Promise<AdminResponse>`, **inteiro** dentro de `this.prisma.$transaction(async (tx) => …)`, com esta ordem exata de passos, todos no `tx`:
      1. `await tx.$queryRaw\`SELECT "id" FROM "Person" WHERE "organizationId" = ${organizationId} AND "isAdmin" = true ORDER BY "id" FOR UPDATE\`` — trava **toda** linha que administra a organização hoje, **antes** de contar. Comentário obrigatório no código explicando por quê: sem o lock, duas transações simultâneas leem cada uma "há duas administrações" e as duas escrevem — é *write skew*, que o `READ COMMITTED` do Postgres não impede porque cada `UPDATE` só tranca a própria linha; com o lock, a segunda espera ali, relê depois do commit da primeira e cai no 409. `ORDER BY "id"` para duas transações nunca travarem as mesmas linhas em ordens opostas. O `organizationId` vai como **parâmetro interpolado pelo Prisma**, nunca concatenação de texto.
      2. `const person = await tx.person.findFirst({ where: { id: personId, organizationId }, select: { ...adminFields, isAdmin: true } })`; se não achar, `throw new DomainNotFoundException(PERSON_NOT_FOUND_MESSAGE)` (a constante já existe no arquivo).
      3. Só **se** `person.isAdmin`: `const others = await tx.person.count({ where: { organizationId, isAdmin: true, id: { not: personId } } })`; se `others === 0`, `throw new ConflictException(LAST_ADMIN_MESSAGE)`; senão `await tx.person.updateMany({ where: { id: personId, organizationId }, data: { isAdmin: false } })`. Quem **já é membro** não passa por nada disso: nenhum `count`, nenhum `updateMany`, e o retorno é 200 (R6) — rebaixá-lo não diminui a contagem, e um 409 ali seria recusa inventada.
      4. Retorno com **destruturação explícita**: `const { id, name, email } = person; return { data: { id, name, email } };` — `isAdmin` foi lido para decidir e não pode vazar para um corpo que o contrato não tem.
    - **`count` das *outras*** (`id: { not: personId }`), e não "quantas existem, comparado com 1": contar as outras é a pergunta que a regra faz, e vale igual para si mesmo e para outra pessoa.
    - **`findFirst` com `organizationId` no `where`, nunca `findUnique` por id**, e **sem `isUuid`**: id malformado, inexistente e de outra organização caem no mesmo 404 (R12), pela mesma razão já escrita em `unit-assignments.service.ts`.
    - **`updateMany`, e não `update`**: o escopo de organização vai no `where` da **escrita**, não só na leitura anterior.
    - **Por que o lock, e não `isolationLevel: 'Serializable'`**: o `Serializable` devolveria `40001` para uma das transações e obrigaria um laço de repetição — o primeiro do projeto e fonte de teste instável. O `FOR UPDATE` faz a segunda **esperar** e **reler**. Promover (114) não precisa de lock: só aumenta a contagem.
    - **Auto-rebaixamento não é caso especial**: o código não compara `personId` com quem chama. O `AdminGuard`, que relê `isAdmin` do banco a cada pedido, faz o papel novo valer no pedido seguinte — inclusive para o `GET /admins` da própria página, que passa a responder 403.
    - `admin-roles.controller.ts`: um `@Delete(':personId')` que recebe `@CurrentPerson() person` e `@Param('personId') personId: string`, chama `demote(person.organizationId, personId)` e devolve `Promise<AdminResponse>`. **Nenhum `@UseGuards` por método**: o `@UseGuards(SessionGuard, AdminGuard)` da classe já cobre o método novo, e é isso que o comentário que já está lá (citando as fatias 114 e 115) promete. O `CsrfGuard` global (`APP_GUARD`) cobre o `DELETE` sem uma linha a mais. Sem `Logger` e sem `console.` fora de testes.
  - Skills: security, authorization
  - Complexidade: alta
